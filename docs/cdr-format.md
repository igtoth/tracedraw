# CDR format notes

What the reader assumes, and what has been confirmed. Status legend:

- **confirmed (public spec)**: matches the public, declarative description
  of the format (a Kaitai Struct specification built from observed files).
  We use that description as documentation only; no code is taken from it.
- **confirmed (file)**: checked against a named file in our corpus.
- **assumed**: from public reverse-engineering notes or our own reading,
  not yet checked.
- **wrong**: kept for history.

Versions in this document are the format's major numbers (7 to 21 and
up), as the RIFF form type encodes them (`CDR7` to `CDR9`, then `CDRA` =
10 onwards, skipping `I`). The public spec writes them as hundreds
(1300 = version 13); `vrsn` stores the same number.

| Item | Status | Note |

### Versions 3 and 4

Version 3 files (form type `CDR `, `vrsn` 300) and version 4 files use
the RIFF layout with 16-bit fields. Sources: four version 3 drawings and
six version 4 drawings a user sent, five of them also in version 5, and a
large set of version 3 clipart files a user sent (none committed); every
file opens, and renders were compared across the versions of each
drawing.

| Item | Status | Note |
|---|---|---|
| Version 3 object types count from 0: rectangle 0, ellipse 1, curve 2, text 3, bitmap 4 | confirmed (file) | Read as the later codes plus one. |
| Version 3 object (`lobj`) arguments: 100 transformations, 30 coordinates, 20 fill, 10 outline, all inline | confirmed (file) | |
| Argument 100: u16, count (u16), then 10-byte entries (type u16, data offset u16 at 6); type 0x8c is a matrix of six i32 (a, c, e, b, d, f; factors 16.16, offsets 1/1000 inch); matrices apply in file order | confirmed (file) | See the envelope row. |
| Transformation type 0x14 (version 3) is an envelope: two u16, the box it maps from (four i16: left, top, right, bottom), the indexes of the corner points and the point count (five u16), then the points, clockwise from the bottom-left corner up the left side, three a cubic segment, the last closing on the first. Matrices before it apply first, then the envelope maps the box onto its outline, then the matrices after it | confirmed (file) for the layout and the shapes it bends in charts and drawings; the mapping between box and outline is assumed (ours blends the four sides) | Text and groups under an envelope keep their matrices only, with a warning. |
| Blend (versions 9 and 13): the intermediate steps are not stored. Between the two end objects stands an empty `LIST lnkg` whose own `lgob` holds a `loda` of object type 7 with two arguments, of types 12020 (begins with u32 2) and 3000 (its first u32 is the step count, then u32 254000). The ends are the objects just before and after the group in the list; the first one (the upper one) gets a live blend to the second, and the steps lie between the two. In the 3000 argument, 24 bytes after the step count, the centres of the two ends' boxes (two coordinate pairs, the later object's first in both files), then u32 1920 (0x780, meaning unknown); the bytes between hold zeros (version 9) or leftover memory (version 13). The steps pair the two outlines node for node from each one's first node, as the nodes run, without matching them by shape: a rectangle from its corner at the origin along its height first, a polygon from its top vertex clockwise. Each node of a step lies on the straight line between its paired nodes, so a step between a rectangle and a pentagon is a pentagon with sharp corners; the rectangle gains its fifth node halfway along its last side (the one closing back to its first node). So the steps turn, and fold flat in the middle when the outlines run opposite ways | partly understood (two files, one blend each, default 20 steps) | The step count's place is assumed from the default value; a value there outside 1 to 999 (no count the program saves) means the field holds something else in that file, and the blend gets the default 20 steps with a warning naming the value (it was kept to 999, #980). All the blends of one file take at most 100000 steps together; past that a blend gets what is left, at least one step, with a warning; acceleration, rotation, colour direction and blends along a path are not read (defaults). The node pairing is matched to how the two files look in the program that saved them; the rectangle's node order and where its added node goes are inferred from those two pictures; with two or more nodes missing, the last side is assumed to be cut into equal parts (not seen in a file). The colours the steps and ends take on screen (CMYK shown as RGB) are not matched to those pictures. A contour's linked group is object type 15 and keeps its steps as objects. |
| Version 3 group (`grp `) `lobj`: argument 100 places all the group's objects | confirmed (file) | Without it, grouped objects come out small and out of place. Version 4 groups have a `trfd` too, but their objects already carry their whole transform. |
| Version 4 `trfd`: the same fixed-point matrix after the record type 8 | confirmed (file) | Several matrices compose, as in later versions. |
| Inline fill (version 3): type u8 (0 none, 1 uniform, 2 linear fountain, 4 radial fountain, 6 PostScript texture, 7 two-colour pattern, 10 vector pattern), then a colour; or the angle (i16, tenths of a degree) and two colours; or (7) the tile id (u32, a `bmpf` id), tile width and height (u16), 7 bytes, front and back colours | confirmed (file) for 0, 1, 2 and 7; 4 assumed | Types 6 and 10 show a stand-in of grey stripes (the PostScript texture is a procedure named by number only; the vector pattern's `LIST vect` is not read yet). |
| `bmpf` of version 3: rows padded to 2 bytes (a 16 x 16 tile in 32 bytes) | confirmed (file) | Later versions pad to 4. |
| Inline outline (version 3): flags u8 (bit 0 = outlined), width u16 (1/1000 inch), stretch u16, angle u16 (tenths), colour, caps at 32, joins at 33, start and end arrowhead ids (u32 at 34 and 38) | confirmed (file) for flags, width, colour, caps, arrowheads; joins and angle assumed | |
| Colour, version 3: model u8, four bytes. Model 1: CMYK in percent. Model 0: u16 index, u16 tint; 0 black at the tint, 1 white, other indexes colours of a numbered ink library | confirmed (file) | Library colours become spot inks named by number; their look comes from the file's thumbnail. |
| Colour, version 4: model u16 then four u16 (model 1: CMYK in percent; model 0: index and tint) | confirmed (file) | Model 1 was read as a library colour before. |
| Curve coordinates before version 6: u16 count, a u16 (1 in glyph outlines of versions 3 and 4), then the points | confirmed (file) | The two were read as one u32, which broke such curves. |
| `arrw`, versions 3 and 4: id (u32; version 4 a u16 and the u16 10), u16, point count (u16 at 6), points offset (u16 at 8, from byte 6), node types at 10 (12 when the u16 at 10 is 1), points as i16 pairs | confirmed (file) | Version 4 outlines name them by the low 16 bits. |
| Version 3 artistic text (coordinates argument): count u16 at 11, font u16 at 15, character spacing, size (1/1000 inch), word and line spacing at 17, 19, 21, 23, alignment at 25, tab stops from 32, 3-byte character records from 132 (the character in the middle) | confirmed (file) for count, size, characters; spacing and alignment assumed | The family is the first name of the `ftbl` table; how the font number picks among several names is not known. |
| `imhd` (version 3): a `.bmp` thumbnail of the drawing's extent, 16 colours, dithered | confirmed (file) | Used to colour library inks (mean of the samples). |
| `mcfg`, version 3: two unknown bytes, then the page corners, y down | confirmed (file) | |

### Versions 1 and 2 (`WL`)

Files of the first two versions are not RIFF. Everything here comes from
18 files a user sent (not committed), one of which was also sent saved in
version 5; renders of all 18 were compared with what the drawings plainly
show. Values are little-endian; lengths in thousandths of an inch.

| Item | Status | Note |
|---|---|---|
| `WL`, a marker byte (`d`, `e` seen), a zero, then five u32: settings start (28), records start, records end, trailer start and that minus two | confirmed (file) | `wl.rs` |
| Page box: four i16 at byte 30 (left, top, right, bottom) around the page centre | confirmed (file) | Letter portrait in every file seen. |
| Font table at the records' end: u16 count, then 84 bytes a font (u16 id, u16, the `.wfn` file name) | confirmed (file) | The shipped font files are mapped to current families by name (assumed). |
| Group and layer records: 28 bytes, flags at 26 low byte other than `0x40` | confirmed (file) | Groups are flattened. |
| Drawn object: flags `0x40` at 26, u16 body size at 28, record length = size + 32 | confirmed (file) | The walk ends exactly at the records' end in all 18 files. |
| Object fields: point i16 x2 at 32, matrix 6 x i32 16.16 at 36 (a, b, tx, c, d, ty; `x' = a x + b y + tx + point`), type at 60 (0 rectangle, 1 ellipse, 2 curve, 3 text) | confirmed (file) | |
| Outline: flag at 67, u16 width at 68, colour at 74; fill: type at 94 (0 none, 1 uniform), colour at 95 | confirmed (file) for uniform; other fill types assumed none | Texture fills of one file are not read. |
| Colour: model byte, then four bytes. Model 1: C, M, Y, K in percent. Model 0: u16 index, u16 tint; 0 black, 1 white | confirmed (file) for models 1 and 0 with indexes 0 and 1 | Other indexes read as black with a warning. |
| Rectangle: i16 width and height from byte 114, corner radius at 120; ellipse: width, height and two angles at 118 and 120 | confirmed (file) for sizes; radius and angles assumed | Arcs and pies are drawn whole, with a warning. |
| Curve: u16 count at 114, points from 118, node types after them as in later versions | confirmed (file) | |
| Text: spacing of characters, words and lines in percent at 116, 118, 120; font id at 122; size u16 at 125; alignment at 127 (1 left, 2 centre); count at 128; characters from 140, CR LF between lines | confirmed (file) for font, size, count, characters, centre alignment and line spacing; character and word spacing assumed | The byte at 124 (1, 2, 4) is probably the weight or slant; not read. |
| Records run from front to back | confirmed (file) | Backgrounds come last in the files. |

## Structure

| Item | Status | Note |
|---|---|---|
| `LIST page` > `LIST layr` > `LIST obj ` > `loda` + `trfd`; groups (`LIST grp `) nest `obj ` lists and other `grp ` lists | assumed (layer > obj confirmed, file: banner, version 21) | Spec types the chunks but not the nesting. `grp ` lists become groups; other lists under a layer are descended, so an object list one level down is still found. |
| `LIST lnkg` (a linked group: the strokes an artistic brush draws along a curve): its own `LIST lgob` with a `loda` and a `trfd`, then `obj ` lists whose `trfd` is the identity; the group's matrix places them. A group's (`grp `) children carry their whole transform | confirmed (file: a version 10 tutorial logo; its three brushed curls land in the cup only with the linked group's matrix, as its preview shows) | The `lnkg` matrix is applied before each object's own. |
| `flgs`: 4 bytes; byte 3 is the record type (0x08 object, 0x10 group, 0x90 page, 0x98 layer); for pages byte 2 != 0 marks the master page; for layers byte 0 is the layer type (0 normal, 0x08 desktop, 0x0a guides, 0x1a grid) and byte 2 is set on a layer of the master page (pages list the master's guides and desktop layers again) | confirmed (public spec; byte 2 and the repeated entries in public sample files of versions 11 to 22) | Guides and grid layers (type & 0x0f = 0x0a) are imported hidden and unprintable. | Layer name: `loda` argument 1000 in the layer's own `loda`: NUL-terminated single-byte text before 12 (system code page), UTF-16LE from 12 | confirmed (public spec) | Single-byte text is decoded as Windows-1252 (the spec's own default; the real code page is the saving system's). |
| `lobj` has the same layout as `loda` | confirmed (public spec) | |
| `bbox`: four coords (two corners); `obbx`: eight coords (four corners) | confirmed (public spec) | Not used; we compute bounds. |
| `spnd`: u32 (u16 before 6); `usdn`: u32 static object id | confirmed (public spec) | Not used. |

## How to confirm an item on a file

1. Take a small `.cdr` file of your own holding one object and note its
   version (`cargo run -p tracedraw-cli -- info file.cdr`).
2. `cargo run -p tracedraw-cli -- inspect file.cdr` dumps the chunk tree.
3. Compare the parsed values with what the file is known to hold
   (position in mm, size, colour values) and move the row to "confirmed
   (file)" with the file name. Add the finding, its source and the date
   to `CLEANROOM.md`.

## Version 8 text frames

Version 8 files come in two layouts the version number does not tell apart: the usual one (800) with paragraph text frames of 32 bytes after the matrix and path flag, and the bidirectional one (801) with 34. The reader tries 32, and when the counts that follow are implausible, 34; the style table likewise is read without the set11 table first and with it when that reads with complaints (2026-10-19, from version 8 samples a user attached to a bug report).
